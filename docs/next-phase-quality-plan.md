# 下一阶段计划：真实任务质量与执行效率

> 状态：连续分页、文件范围约束和来源摘录已实现；后两者保留为 Host API/内部能力，不在普通输入框提供重复入口。确定性验证见末尾，真实模型复测待进行。[接口说明](task-constraints-usage.md)

## 目标

用固定的真实任务回答两个问题：结果是否正确，完成任务是否花了不必要的时间和 token。

当前已打通交付展示、检查记录、执行诊断和模板。已有真实 E2E 主要验证流程能跑通；报告存在、命令退出成功，还不足以证明内容正确或审查质量稳定。

## 实施顺序

| 阶段 | 做什么 | 交付物 |
|---|---|---|
| 1. 建立基线 | 选 12 个固定任务，覆盖文档总结、文档对比、代码修改、连续修改；每类 3 个，明确输入、预期结果和不能发生的行为 | 任务样例、验收规则、首轮结果表 |
| 2. 修复主要问题 | 根据结果选最影响使用的 2～3 个问题修复，例如漏读、重复读取、修改不完整、检查失败却声称成功 | 小范围代码或提示词调整、对应回归用例 |
| 3. 对比验收 | 使用相同模型配置和任务复测；重点任务重复运行，记录波动 | 改造前后对比、剩余问题和下一步建议 |

## 怎么判断结果

- **文档总结：** 关键事实是否覆盖，是否出现原文没有的信息。
- **文档对比：** 是否找齐预先设置的差异，来源位置是否正确。
- **代码修改：** 指定行为是否通过独立检查，是否误改范围外文件。
- **连续修改：** 新要求是否落实，上一轮已有内容是否被意外破坏。

每个任务同时记录完成情况、实际耗时、模型调用次数、工具调用次数，以及模型上报的输入、输出和缓存 token。不能只看总 token 大小就认定浪费；没有记录的指标标为未知。

## 改动边界

- 复用现有真实 E2E、Trace 和统计代码，用测试样例和结果文件完成评估。
- 模型的阅读、核对和收尾习惯放在 Harness；工具错误修工具；汇总在 Host；显示问题在前端。
- 根据实际失败决定是否需要更明确的工具结果字段，避免继续堆文本匹配规则。
- 本阶段不增加新的用户面板，不引入评测平台、多 Agent 或长期记忆系统。

## 完成标准

12 个任务都有可核对的结果；修复项有针对性回归；改造前后在同等条件下比较，结果正确性不退步。效率改进必须有数据支持，仍然失败的任务如实保留。

先完成基线，再决定优化目标与幅度。实现前不承诺节省比例，也不把一次运行通过当作稳定性证明。

## 硬约束实施结果（2026-09-20）

[硬约束方案](quality-hard-boundaries-plan.md)三件事已全部落地并通过确定性验收：

- **文件范围硬约束**：Host 固化 `writeScope`（`src/sandbox/write-scope.ts`），write/edit/move/delete 执行前校验；受限任务禁止 createDir，Shell 强制只读（复用 macOS/Windows 只读沙箱）。证据模式任务自动只读。
- **来源证据模式**：Host 固化来源版本（sha256），`renderEvidence` 校验引用行号并提取原文渲染；校验失败拒绝发布，不由模型补写。Harness 注入输出契约（`setTaskConstraints`），模型自由文本不再直接展示。
- **入口边界**：普通 Web 输入只保留现有权限菜单。精确文件范围与来源摘录通过显式 Host API 参数或受控内部流程使用，不与工作区权限并列展示。
- **验收**：`tests/write-scope.test.ts` 12/12、`tests/task-constraints.test.ts` 11/11、`tests/task-constraints-host.test.ts` 5/5；全量确定性回归 96 套件通过（18.3 秒，日志 `.payaso/logs/run-all-2026-09-20T01-29-34-129Z.log`）。macOS 沙箱实际拦住重定向、子进程、Node 脚本和软链接写入；类型检查与前端构建通过。
