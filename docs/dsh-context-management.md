# DSH 上下文处理机制详解

- **记录日期：**2026-09-30
- **对象：**DeepSeek Harness（DSH）的上下文管理设计
- **目的：**逐条讲清 DSH 的实现与设计理由，作为 PayasoAgent 对照与借鉴的依据
- **配图：**[dsh-context-flow.html](dsh-context-flow.html)（可视化流程图，自包含 HTML）

> 本文是**只读研究记录**，描述的是 DSH 的实现，不代表 PayasoAgent 已做任何改动。

## 一句话框架

> **在「容量阀」之前先铺几道几乎免费的绝对预算闸门（投影），容量阀（压缩）只当最后兜底；全程有 token 计量，但没有成本预算。文本和图片是两条并行轴，各有一套独立的预算和降级逻辑。**

真正花钱的只有一步——**摘要**。而它前面已经有两道免费闸门把体积削掉了，所以轮到它时往往已经没什么可压。

## 底座：一本「只增不改」的账本

DSH 所有机制都建立在一个前提上：**会话是一个只能追加、不能原地修改的事件日志**。

想"改"历史怎么办？**不改，而是记一条新事件说明"我对第 X 条做了什么"**。例如把某张旧图换成文字，不是删掉那条消息，而是记一条 `image/offload` 事件。

**为什么这么做很关键：**

- 原文永远在账本里，随时能查、能回放
- "省略 / 压缩 / 修剪"都是**记录下来的决定**，换模型、恢复会话、重放，效果一致
- 想撤销也有据可依
- 投影是**纯函数**（同样的账本 → 同样的结果），所以下游不需要信任何隐式状态

**类比：**像记账，写错了不涂改，而是再记一笔"冲销"。账本永远完整。

## 第 0 道：秤（token-meter）

**是什么：**一个纯计算服务，**不发模型请求、不花钱**。它把账本从头"放一遍"，算出当前请求有多重。

**要点：**

- **结果确定**：同样的账本，谁来算都一样。所以压缩决策、界面占用显示、监控遥测用的是**同一个数**
- **计价分三种**：文字用固定启发式；图片在适配器声明了视觉计价时按「14px patch 网格、3:1 降采样、544×544 放大下限、单图上限 1024 token」算；文件按「模型可见的句柄文本」计价
- **只在请求完全相同时**才直接复用 provider 上报的 usage

**类比：**体重秤。站上去就给数，不用为此跑一趟医院。

---

## 第 1 道门：单条闸（spill —— 大输出"存档案柜"）

**什么时候拦：**工具一执行完，**立刻**拦（监听 `ctx.tools`）。

**拦什么：**文字 + 图片**共享**一个 token 预算（典型配置 `maxInlineTokens: 12500`）。

**怎么处理：**

1. 把**完整内容写进文件**（spill 落盘，本地会话级私有文件）
2. 模型只拿到：**开头 + 结尾 + 那个文件的路径**
3. 模型想知道细节，自己按路径用 `read` / `read_image` 读回来
4. 如果连文件都存不了 → **保留原文**（宁可大，不能丢）

**类比：**秘书收到 100 页报告，不会全摊在你桌上，而是**收进档案柜**，给你一张卡片："在柜子 A-3，开头结论是 XXX，结尾是 YYY，细节自己取。"

**效果：**大输出**从一开始就进不了上下文**，后面所有门的压力都变小。

**关键参数（spill-policy）：**

| 字段 | 默认 | 含义 |
|---|---|---|
| `maxInlineTokens` | 省略（关闭策略） | 文字、图片、图片说明和提示共享的估算 token 上限；省略时禁用 |

## 第 2 道门：总量闸（压缩家族）

在**每一步请求发出之前**检查（监听 `agent/pre-step`）。内部有**三步，按"单价"从便宜到贵**。

### 2.1 pruner —— 砍中段（免费）

- **触发条件**：只有总量闸已经报警才跑。**没报警就一个字节都不动**
- **预算**：按**字符**算
- **怎么砍**：留**前 4096 字** + 一句「middle pruned」标记 + **后 1024 字**，中间全扔
- **不发模型请求**，完整原文仍保留在会话日志中
- **最妙的一点**：砍完如果总量已达标，**后面的摘要就不用做了**——省掉一次模型调用

**类比：**一篇文章太长，只留开头和结尾，中间写"（此处省略 3000 字）"。

| 字段 | 默认 | 含义 |
|---|---|---|
| `thresholdChars` | `8192` | 合并文本超过此 Unicode 码点数时修剪 |
| `headChars` | `4096` | 保留的开头码点数 |
| `tailChars` | `1024` | 保留的末尾码点数 |

### 2.2 保留 —— token 尾巴（不花钱）

- 预算默认 `(W − O) × 0.16`，也可配成**绝对值** `retainTokens`（两者互斥）
- 从**最新消息往回数**，数够预算为止，这段**一字不改地保留**
- **裁剪单位是"工具调用对"（step），不是整轮**：可以切进一轮中间，只压掉已经闭合的前几步
- **唯一硬约束**：不能把"进行中的工具调用"劈开
- **system 永不动**（它是账本的第 0 号节点，任何压缩范围都从第一个非 system 节点开始）
- **没有"当前轮保护"**：当前轮只因为落在尾巴预算内才没被切；一轮太长，照样切进来

**类比：**搬家时最近要用的留手边、旧的装箱——但装箱不能把配套的东西拆开（调用与结果必须成对）。

| 字段 | 默认 | 含义 |
|---|---|---|
| `retainRatio` | `0.16` | 逐字保留的近期对话占 `(W−O)` 的比例；与 `retainTokens` 互斥 |
| `retainTokens` | — | 逐字保留的绝对预算；必须低于已解析阈值 |

### 2.3 摘要 —— compaction-basic（唯一花钱的一步）

- **触发线**：`floor(min(W × 0.8, W − O − 65536))`
  - 注意第二项：**额外留 65536 token 的绝对余量**，不让阈值纯随窗口漂
- **目标**：把最旧的"平衡范围"换成**一条摘要消息**，近处尾巴保持逐字不变
- **校验**：摘要**必须真的让内容变短**，否则整个事务作废（"拒绝不缩小源内容的摘要"）
- **重试**：`compactionRetries: 1`；被 provider 拒了再救 `maxOverflowRetries: 1`

**这一步最值钱的设计：摘要请求"骑缓存"**

DSH 让模型写摘要时，**不是随便发一个"帮我总结这些"的新请求**，而是**故意拼成跟上一个真实请求一模一样的前缀**：

```text
[system（账本 0 号节点原样）+ 上次请求用的工具 + 被压缩区域的消息] + [追加一句：请总结]
 └──────────────────── 与上一次请求逐字相同 ────────────────────┘   └── 只有这是新的 ──┘
```

provider 的前缀缓存因此仍可命中，只有最后那句指令和输出是新的。**为了压缩而付的那次调用，几乎不额外花钱。**

**崩溃安全（区域事务）**

压缩不是"直接改"，而是一个事务，在账本里留一对标记：

```text
compaction/start  …（写摘要）…  compaction/summary + 替换消息 …  compaction/end
```

中途崩了会留下"未配对的 start"。这个标记**本身就是一个持久锁**——下次启动看到它就知道"上次压缩没做完"，不会糊里糊涂继续。官方描述："位于较新边界之前的未匹配标记是陈旧证据，不会阻塞；位于该边界之后的标记报告 `busy`。"

| 字段 | 默认 | 含义 |
|---|---|---|
| `thresholdRatio` | `0.8` | `floor(min(W × thresholdRatio, W − O − headroomTokens))` |
| `headroomTokens` | `65536` | 路由输出预留之外的额外压力余量 |
| `maxTokens` | `headroomTokens` | 摘要输出上限（含推理 token） |
| `compactionRetries` | `1` | 压力仍超阈值时的额外尝试次数 |
| `maxOverflowRetries` | `1` | 已确认溢出后的最大重试次数；`0` 只禁用恢复 |
| `modelPolicies` | `[]` | 针对个别模型路由的精确 `{ provider, model, ... }` 覆盖 |
| `auto` | `true` | 关掉则仅手动 `/compact` |

## 第 3 道门：溢出闸（被 provider 拒了才救）

前面都在**事前预估**，这一道是**事后补救**（监听 `agent/request-error`）：

- provider 明确报 `CONTEXT_WINDOW_EXCEEDED` → **绕过常规阈值与保留策略**，直接做一次"最大幅度头部缩减"
- 只有确认"账本替换的 generation 前进了"才允许重试——**防止死循环**
- 取消（cancel）全程保持最终决定权

## 图片轴（与文本并行）

**正常情况：**DSH 的 DeepSeek 适配器有 **Files 模式**——图片**作为文件引用发出去，不是 base64 塞进上下文**。回退模式才用 base64，且有独立预算。

**预算：**`maxRequestFilesBytes` + `maxImagesPerRequest`（Files 模式），两种模式都按配置的量子**从最旧前缀开始移除**。

**什么时候降级：**预算超了，provider 返回 `IMAGE_OFFLOAD_REQUIRED`，并告诉你"还需要省略几张最旧的"。

**降级怎么做：**

- 从**最旧的图片**开始，换成一段**模型看得见的文字**：显示名 / 附件 id + 规范化尺寸 + 媒体类型 + **当前只读路径**
- 记一条 `image/offload` 事件 → **永久生效**（切换路由、恢复、回放都保持）
- 重试**不消耗** provider 的重试预算
- **分阶高水位策略**：不是每加一张图就重写一次旧请求前缀，只有跨过水位档才重算一次省略集

**类比：**相册太厚塞不进信封，就把**最旧的几张照片取出**，换一张便签"这里本来有张照片，存在 D-7 抽屉，要看自己取"。

**代价（DSH 自己写明的）：**"提供方缓存只能复用到第一条被修改的消息之前。"降级那一刻缓存会断一次——但换来的是请求能发出去，且之后前缀重新稳定。

## 关键设计点答疑（看着奇怪，其实有原因）

| # | 疑问 | 真正的原因 |
|---|---|---|
| 1 | 为什么不直接改历史，非要"只增不改"？ | 原地改之后就无法回答"原文是什么 / 上次为什么这么压"，审计、崩溃恢复、换模型重放全都依赖原文。改 = 记一条投影规则，投影是纯函数 → 可重放、确定。代价是实现复杂，换来可追溯与一致性 |
| 2 | spill 和 pruner 都是砍工具输出，不重复吗？ | 时机不同：**spill 在工具产出瞬间**（预防，根本不让进门）；**pruner 在总量超限之后**（治疗，处理"当时不大、累积起来才大"的历史）。一个是安检，一个是大扫除 |
| 3 | pruner 为什么不一直跑，只在超阈值后跑？ | 砍中段**有信息损失**。没压力就不动 = 按需付费。而且它免费，所以放在"要花钱的摘要"之前试一次——能省掉摘要就省 |
| 4 | 为什么单条闸按字符、总量闸按 token？ | 单条闸在工具产出瞬间，**那时还没有完整请求上下文**，字符估算够用（快、不必等秤）。总量闸要做决策、要跟阈值比，必须同单位 → 用秤。官方也承认"字符预算只能近似 token" |
| 5 | 为什么裁剪单位是"工具调用对"而不是"整轮"？ | 一轮可能很长（含很多次工具调用）。"整轮保留/丢弃"太粗：要么损失太大，要么根本压不下来。工具调用对是**最小语义完整单元**——调用与结果必须成对 |
| 6 | 为什么没有"当前轮保护"？不危险吗？ | 有保护就有漏洞：**一轮特别长时，保护当前轮 = 永远不能压它 = 卡死压不下来**。DSH 改为靠"保留 16% 尾巴"天然保住最近的；当前轮太长就切进去，只保证不劈开进行中的调用对 |
| 7 | 阈值为什么要 `min(W×0.8, W−O−64K)`？ | 纯 `W×0.8` 的隐患是**窗口越大阈值越松**。`W−O−64K` 是第二条线：保证触发点与窗口上限之间**永远留 64K 绝对缓冲**。取 min = 哪条保守听哪条 |
| 8 | 保留预算为什么是 16%？ | 平衡取值：太小 → 近期上下文不够、模型失忆重复劳动；太大 → 没省下多少。它锚在 `(W−O)` 且**可换成绝对值** `retainTokens`（小窗口模型用绝对值）。这是可调参数，不是定理 |
| 9 | 为什么"拒绝不缩小源内容的摘要"？ | 摘要本身要花一次模型调用。若模型跑偏、摘出来比原文还长，就是**纯亏损**：花了钱、没省空间、还多一条消息。写入前校验"输出必须比输入短" |
| 10 | 为什么图片降级是"永久"的？ | 恢复会立刻**打破前缀缓存**（第一条被改消息之后全失效），且请求形态在多轮间反复横跳。永久 + 记事件 = 降级一次之后前缀稳定，缓存持续命中 |
| 11 | 为什么 spill 要给"路径"而不是直接丢？ | 直接丢 = 模型**永远看不到那份信息**，可能结论错误或重复劳动。给路径 = 信息还在、只是不在上下文里，需要时读回来。这是**延迟加载**，让降级可补救而非信息毁灭 |
| 12 | 为什么要有 `compaction/start` 那对事务标记？ | 压缩要发模型请求，可能失败、被取消、进程崩溃。先改历史再发请求 → 失败就留下"半压缩"坏状态。先记 start（上锁）→ 请求 → 记 summary + 替换 → 记 end，就是数据库事务那套 |
| 13 | 为什么摘要调用要"骑缓存"？ | 摘要要读被压缩的那一大段历史。不骑缓存 = **一次全新冷启动**，把那段又全额 prefill 一遍。**压缩本是为了省钱，不能在压缩时先烧一次大钱** |
| 14 | token-meter 为什么要"回放日志"而不直接数消息？ | 历史**已被各种投影改过**（spill / pruned / offload），直接数 raw 消息会算错。回放 = 按顺序重新应用所有投影规则，得到模型真正会看到的内容体积。纯函数 → 压缩/界面/监控拿到同一个数 |
| 15 | 什么是"分阶高水位"？ | 每来一张新图就立刻重算省略集，会让被改位置不断前移 → 每次改写前缀 → 缓存一直断。设几个水位档，**跨档才重算**，多数请求省略集不变 → 前缀稳定 |

## 与 PayasoAgent 的差距对照

| 维度 | DSH | Payaso 现状 | 差距 |
|---|---|---|---|
| 单条闸（工具结果） | 8192 字符 / 12500 token，超了砍或落盘 | ✅ 16KB（首 6KB + 尾 4KB），生产端执行 | 持平（量级相近） |
| **投影（旧内容降级）** | ✅ **主力**：pruner 砍中段 / spill 落盘 / image-offload | ❌ **完全没有**（`grep` 零命中） | ⚠️ **最大缺口** |
| **图片轴** | ✅ Files 引用，不 base64；超预算降级为文本占位 | ❌ **每次调用把所有历史图 base64 内联**（实测 9 张 = 6.55MB） | 🔴 **致命缺口** |
| 保留 | token 尾巴 `(W−O)×0.16`，或绝对 `retainTokens` | ❌ 全量保留，直到 `W×0.8` | 缺保留预算 |
| 压缩阈值 | `min(W×0.8, W−O−64K)` | `W×0.8` | 同病（容量锚定），DSH 多个 64K 绝对项 |
| 压缩目标 | 压到 `(W−O)×16%` | 压到 `W×0.65` | Payaso 压得太少 |
| 摘要 KV 对齐 | ✅ 骑上一请求真前缀，复用缓存 | ❌ 新建 system+user 两条消息，**冷启动**，且把待摘要内容 JSON 重发一遍 | 缺口 |
| 裁剪粒度 | 工具调用对（step），可切进一轮中间 | 完整轮（turn），当前轮永不裁 | Payaso 粒度粗 |
| 溢出闸 | ✅ 拒收后 → 缩减 → 重试 | ❌ 无（只在发请求前预估） | 缺口 |
| 计量 | token-meter：回放式、确定、三方共用 | `context_usage`（估算）+ 归一化 usage | 持平 |
| **成本预算** | ❌ 缺（账目极细，但没有"值不值"的开关） | ❌ 缺 | **同病** |
| 检索 | 图片/文件路径 + `read_image` 寻回 | 附件清单 + 路径引用 | 持平 |

**结论：**两边底层同病（容量锚定阈值 + 无成本预算），但 DSH 在容量阀之前铺了**单条闸 + 总量闸 + 溢出闸**三层，且**投影是主力**；Payaso 只有单条闸，中间**空了一整层**——而且图片还在每轮被全量 base64 内联，把这条路彻底堵死。

**实测对照（同一份 ≈30 万 token 上下文）：**DSH 的请求体约 **0.9MB**；Payaso 为 **7.47MB**（差值全是 9 张历史图的 base64）。

## 附：参数速查

| 机制 | 参数 | 默认 | 是否随窗口缩放 |
|---|---|---|---|
| 单条闸 spill | `maxInlineTokens` | 省略（关闭） | ❌ 绝对 |
| 投影 pruner | `thresholdChars` / `headChars` / `tailChars` | `8192` / `4096` / `1024` | ❌ 绝对 |
| 保留 | `retainRatio` / `retainTokens` | `0.16` / — | 默认缩放，可切绝对 |
| 压缩触发 | `thresholdRatio` / `headroomTokens` | `0.8` / `65536` | 部分（含绝对项） |
| 摘要输出 | `maxTokens` | `headroomTokens` | 跟随余量 |
| 重试 | `compactionRetries` / `maxOverflowRetries` | `1` / `1` | — |
| 按模型覆盖 | `modelPolicies` | `[]` | 精确 `provider + model` 匹配 |
