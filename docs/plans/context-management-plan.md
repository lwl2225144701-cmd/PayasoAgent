# 上下文管理改造方案

> 依据：[`docs/llm-connect-timeout-2026-09-28.md`](../llm-connect-timeout-2026-09-28.md)（超时排查实测）、[`docs/dsh-context-management.md`](../dsh-context-management.md)（DSH 机制研究）
> 状态：**方案已定，尚未实施**

## 目标

- 把「每轮请求体积」从失控状态压回可控范围，消除长会话"越来越慢、偶发超时"。
- 单条工具结果超限后**可恢复**（有路径可回读），不再是"砍掉就没了"。
- **图片进入独立的体积预算**，不再每轮把全部历史图 base64 重发。
- **压缩后的工作集有硬上界**——靠**保留预算**兑现，不靠触发线（触发线在大窗口下必然失控，见 D 项结论）。
- 真正花钱的摘要只在必要时发生，且**复用 provider 前缀缓存**。

## 问题与实测依据

同一份 ≈30 万 token 上下文，实测数据（详见排查报告）：

| 观测项 | 实测值 |
|---|---|
| 一次 run 的规模 | 20 次 LLM 调用 / 模型时间 962s / 总耗时 **1006s（16.7 分钟）** |
| 上下文规模 | 301K token / 859 条消息 / 0.92MB 文本 |
| 上下文组成（按角色） | tool **60.7%** / assistant 38.4% / user **0.2%** / system 0.6% |
| 上下文组成（按工具） | shell 35.8% / edit 12.2% / read 9.4% |
| **实际 HTTP 请求体** | **7.47MB**（文本 0.92MB + **9 张历史图 base64 6.55MB**） |
| 直接打 API 的请求体 | 0.92MB（未物化图片） |
| 模型本身延迟 | 小提示词首字节 **1.4~2.3s**（模型不慢） |
| 301K 上下文延迟 | 首字节 6.7~13.7s / 总 9.3~38.8s（热）；冷更慢 |
| 当前压缩触发线 | `W × 0.8` = **77.66 万 token**（1M 窗口）→ **永不触发** |
| 当前压缩目标 | `W × 0.65` = 63 万（压得太少） |
| 单条闸 | 16KB **硬编码**，头 6KB + 尾 4KB，**中间直接丢、无路径** |
| 图片 | **完全不过闸**（`guardToolOutput` 只作用于 `normalized.text`） |

**一句话结论**：模型不慢、请求形态没问题；慢在**每轮背着 30 万 token + 7.47MB 请求体**，而唯一的控制手段（压缩）阈值锚在容量上、随窗口漂移，永不触发。

## 目标结构（按层）

```text
Runtime（工具调用管线 · 调用边界）
├── 单条闸：结果超限 → 落盘 + 给路径（可恢复）      ← 研究里的「第一条」
├── 图片预算：只物化最近 N 张；更旧的降级为文本占位  ← 独立项（不属于单条闸）
└── 预算常量：共享叶子模块（沿用 tool-output-budget.ts 模式）+ 可配置

Harness（"给模型看什么"）
├── 投影：旧工具输出确定性降级（pruner 式砍中段）
├── 保留：token 尾巴（压缩后的硬上界），粒度到工具调用对
├── 阈值：W×0.8 ∧ 独立成本上限   ← 不照抄 DSH 的 min(…, W−O−64K)
└── 摘要：Run 边界触发 + 骑上一请求真前缀 + 必须变短

Host（持久化）
└── 投影决策记为事件（永久生效、跨恢复/重放一致）
```

> 分层依据：架构文档 §2 明确 `output-guard.ts` 是"Runtime 侧预算执行点"；`src/harness/` 是注入给 Runtime 的独立层。**动 Runtime 需带回归测试**（§1 "谨慎修改区"）。

## 核心改造

### A. 图片轴预算（Runtime）— P0 · **独立项，不属于「单条闸」**

**问题**：`materializeMessagesForModel` 遍历**所有** messages，把每张图都读成 base64，**没有任何"这张图是第几轮发的"判断**。第 1 轮发的图，第 37 轮还在重发。

**实测证据**：

| 观测项 | 值 |
|---|---|
| checkpoint 里的图 | **9 张**（最早那张在第 1 轮 msg#16 发的） |
| 图片原文合计 | 4.91MB |
| **base64 后合计** | **6.55MB** |
| 请求体 | 文本 0.92MB + 图片 6.55MB = **7.47MB**（实测吻合） |
| 到响应头耗时 | **28.6s**（光上传 + 服务端解析） |

**现状链路诊断**（六步，只有第五步是断的）：

| 步 | 环节 | 归属 | 现状 |
|---|---|---|---|
| ① | 图片进来（用户附件 / `read_image`） | Host | ✅ |
| ② | 归一化 + 入库（sha256 内容寻址、原子发布、`chmod 0444`；>2048² 下采样、≤4MiB） | Host | ✅ 达标 |
| ③ | 发布进 workspace（同卷 hardlink，跨卷回退 copy） | Host | ✅ 达标 |
| ④ | 进 transcript **只存引用**（`{mimeType, path, sha256, width, height}`，不存 base64） | Harness/Host | ✅ 达标 |
| ⑤ | **调用模型前物化（`agent.ts:273`）** | **Runtime** | ❌ **无任何预算：不限字节、不限张数、不限年龄** |
| ⑥ | 发请求 | — | ❌ 全量 base64 → 7.47MB |

> 一句话：**仓库有（②③），引用也对（④），但"发货时不点数"（⑤）。**

**改造**：

1. **物化时加预算**（两个都卡，任一超即降级）：
   - `maxInlineImageBytes` —— 本次请求内联图片的 base64 **总字节**上限
   - `maxInlineImages` —— 本次请求最多内联**几张**
   - 选取顺序：**从最新的消息往回**逐张纳入，撞到任一上限即停。
2. **超预算的图 → 降级为模型可见的文字占位**（不是删除）：
   ```
   [图片已省略：<显示名>，<宽>x<高>，<媒体类型>，只读路径 <workspace 相对路径>]
   ```
   - 模型需要细节时，用现有 `read` / `read_image` 按路径读回——**不加新工具、不加新 schema**。
3. **降级必须成批 + 单调**（避免"一张一张挤"导致前缀反复改写）：
   - **成批**：设硬上限 `maxInlineImages` 与批量 `B`；内联张数涨到硬上限时，**一次性降一批**到低水位，而不是每来一张新图就重算。
   - **单调**：已降级的图**不再恢复**（不因为"又有余量了"而回填）。
   - 目标：多数请求的降级集合保持不变 → 前缀稳定 → 缓存持续命中（对应 DSH 的「分阶高水位」）。
   - 由于消息只追加，降级集合可由当前消息列表**确定性推导**，**无需持久化**。
4. **不动 transcript / checkpoint**：降级只发生在模型视图（物化副本）上，canonical transcript 里的引用保持不动——原文永远可追溯。
5. **参数可配**（不学现在把常量写死），并可按模型覆盖（不同 provider 的图片预算差异很大）。
6. **视情况加一条可观测事件**：如 `image_inline_dropped { inlineCount, droppedCount, inlineBytes }`，便于验证与排查。

**不照抄的部分（有意简化）**：

DSH 走的是「**客户端尽力 + 等 provider 拒绝（`IMAGE_OFFLOAD_REQUIRED`）才知道超了**」，因为它的目标是**榨干 provider 给的每一分预算**——所以必须跟 provider 的字节/量子规则精确对齐，复杂度高。

咱们**不需要**：自己定一条可预测的规则（最近 N 张 / 总字节上限）就够，**不依赖 provider 拒绝**，实现简单、行为可预测。

**改动落点**：

| 文件 | 改什么 |
|---|---|
| [`src/runtime/image-materialize.ts`](../../src/runtime/image-materialize.ts) | 加预算判断 + 降级成文字占位（核心改动） |
| 配置（新增） | `maxInlineImageBytes` / `maxInlineImages`（+ 批量） |
| [`src/runtime/trace.ts`](../../src/runtime/trace.ts) | 可选：降级事件（可观测） |
| `tests/` | 超预算 → 只内联最近 N 张、更早的变文字；成批/单调性 |

> **分层约束**：本项在 **Runtime**（调用边界）。架构文档 §1 要求"Runtime 改动需带回归测试"。

**预期收益**：请求体 7.47MB → **~1MB**；"到响应头 28.6s"回到正常区间；单次调用延迟落回 15~25s。

### B. 单条闸可恢复（Runtime）— P1 · **这就是研究里的「第一条：单条闸」**

> 对应「跟 DSH 逐条对照」表里被圈出的那两行：
> **超限后** —— DSH「全文落盘 + 给路径」 vs 咱们「直接丢掉中间，没有路径」
> **能恢复吗** —— DSH「✅ 能（read/grep 读回来）」 vs 咱们「❌ 不能（中间真的没了）」
> 本项就是把这两行补上；其余行（位置、砍法、单一来源）现状已达标。

**问题**：`sliceTextToBudget` 超限后只做 `head + [OUTPUT TRUNCATED] + tail`，**中间内容永久丢失**，且**没有给模型任何恢复途径**。

**实测证据**：

| 观测项 | 值 |
|---|---|
| `events` 表里**最大**的 `tool_result` | **16703 字节 ≈ 16.3KB** |
| 这说明什么 | **正好卡在 16KB 预算上** → 落库的也是砍过的，**原文从未被写进任何持久化存储** |
| 完整原文的去向 | 只在内存里存在一瞬间（`rawResult` 离开作用域即被回收） |
| spill / 落盘 / artifact 类机制 | `grep` 全仓 **零命中** |

**现状链路**（断在哪一目了然）：

```text
工具 execute() 返回 rawResult
        │
normalizeToolResult(rawResult) → normalized.text
        │
validateToolResult(rawResult)          ← 唯一看到完整原文的地方
        │
guardToolOutput(normalized.text)       ← 超 16KB → head + [OUTPUT TRUNCATED] + tail
        │
const result = guarded.content         ← 之后 trace / scratchpad / messages / recovery 全用它
        │                                  （代码注释原话）
        ▼
rawResult 离开作用域 → 被回收          ← 全量内容从未落盘
```

**关键约束（咱们跟 DSH 不一样，直接决定实现方案）**：

DSH 那条链路能成立，靠的是一个前提：**它的 `read` 能读工作区之外的路径**——其文件系统策略"**记录观察结果并设置写保护，但不会把读取限制在工作区内**"，所以 spill 文件放在私有应用目录也能被模型读回。

**咱们不满足这个前提**：

> `src/tools/filesystem.ts` 的 `rejectPath()`：**"仅允许工作区内相对路径，禁止穿越 / 绝对路径 / symlink 逃逸"**，越界一律 `BLOCKED`。

**所以照抄"写进 `~/.payaso/...` 私有目录 + 给模型绝对路径"是读不回来的。** 两条出路：

| 出路 | 评价 |
|---|---|
| ❌ 放宽 `read` 的读取白名单 | **不动**——会削弱既有安全边界（架构文档的显式设计） |
| ✅ **复用既有模式** | 咱们**已经有先例**：运行时产物 → hardlink 进工作区 → agent 可读。附件就是硬链到 **`input/attachments/`**（只读、同名加后缀、永不覆盖）。spill 沿用同一模式即可，**不引入新的安全放宽** |

**改造**：

1. **存储位置沿用既有模式**：落进工作区里 agent 可读的目录（`input/spill/`，与 `input/attachments/` 同级），并复用"入库 + hardlink + 只读 + 永不覆盖"的既有语义（复用附件库的 `putAttachmentObject` / `publishAttachmentIntoWorkspace`，**不新建第二套存储**）。
   - **幂等命名**：文件名 = 工具名 + 内容 sha 前 16 位，同一份内容永远得到同一个路径——工具重复输出同样内容是常态，不该在 `input/spill/` 里堆 `-2`/`-3` 副本，模型拿到的句柄也保持稳定。
2. **超限时**：全文写入 store；模型拿到 **head + `[OUTPUT TRUNCATED]` + tail + 该文件的 workspace 相对路径**。
3. **模型用现有 `read` / `grep` 按相对路径读回**——**不加新工具、不加新 schema**（这是 DSH 明确坚持的做法，也是咱们应该坚持的）。
4. **fail-soft**：写盘失败 → **保留原结果**（宁可上下文大，不能把数据弄丢）。
5. **防循环（结构性豁免，无需显式跳过）**：`read` 自己的输出被 `sliceNumberedWindow` 卡在 `16KB − 2048` 预留之内，**结构上够不到 guard 的预算**，因此永远不会被二次落盘——不存在"读 spill 文件 → 又落盘 → 再读"的循环。
   （DSH 需要显式跳过 `read`，是因为它的 spill 跑在 `tools/post-execute` 另一层、read 结果可能超限。咱们这层不需要，加了反而是多余的 `if`。）
6. **参数可配 + 叶子模块**：预算常量继续放 [`src/tool-output-budget.ts`](../../src/tool-output-budget.ts)（其文件头注释明确了它是"leaf module，两层共用"），保证 **"宣称的契约 == 执行的契约"**；参数改为可配置。
7. **生命周期**：spill 文件需要清理策略（跟随会话删除，或启动时清扫超龄孤儿）——参照附件库已有的 `sweepAttachmentTmp` / 启动清扫做法。

**不照抄的部分（有意简化）**：

DSH 用的是「**不透明定位符 + 检索提示 + 可插拔后端**（本地文件 / 远程 URI / 数据库键）」，因为它的消费方可能是远程或 ACP 环境，路径没有意义。

**咱们只跑本地**：**直接给 workspace 相对路径**就够，**不需要定位符抽象层**——省一层间接，也不会因为"后端可换"而引入多余的失败面。

**改动落点**：

| 文件 | 改什么 |
|---|---|
| [`src/tool-output-budget.ts`](../../src/tool-output-budget.ts) | 叶子模块：预算参数改为可配置，暴露 spill 判定所需信息（保持两层共用） |
| [`src/runtime/output-guard.ts`](../../src/runtime/output-guard.ts) | guard 结果带上"可 spill 的完整原文"与所需元信息 |
| [`src/runtime/tool-invocation/process-manager.ts`](../../src/runtime/tool-invocation/process-manager.ts) | 调用点（`:418`）：超限时写 store，并用"头尾 + 路径"版本替换结果 |
| 新增（spill store） | 落盘 + 清理（优先复用附件库，避免第二套存储） |
| [`src/tools/filesystem.ts`](../../src/tools/filesystem.ts) | `read` 结果跳过自动落盘（防循环） |
| [`src/runtime/trace.ts`](../../src/runtime/trace.ts) | 现有 `tool_output_truncated` 事件**增加 spill 路径字段**（可观测：这次有没有存下来） |
| `tests/` | 超限可读回 / 写盘失败 fail-soft / `read` 不二次落盘（防循环）/ 清理 |

> **分层约束**：本项在 **Runtime**（工具调用管线）。架构文档 §1 要求"Runtime 改动需带回归测试"。

**预期收益**：

- 消除"砍掉就没了"——模型能自助回读被砍的中间内容，**不再需要重跑一遍命令**。
- 为 P2 的投影（C 项）提供"可回查"的兜底：投影是有损的，但有 spill 兜着。
- 保持上下文体积不变（头尾 + 一个路径），**不增加每次请求的负担**。

### C. 投影：旧工具输出的确定性降级（Harness）— P2

**问题**：`tool` 消息占上下文 60.7%（433 条，中位数仅 1KB——不是巨无霸，是几百条碎块累积）。

**改造**：

1. 保留最近 2~3 轮工具结果**全文**；更早的做**确定性截断**（head + 标记 + tail）。
2. **零 LLM 调用**；canonical transcript 与 checkpoint **不改写**（原文可追溯）。
3. 只截 `tool` 消息的 `content`，**保留 `role` 与 `tool_call_id`**，不破坏工具调用配对结构。
4. 每轮只对"新变老"的那一轮动手，天然平滑、无突刺。

### D. 保留、阈值与粒度（Harness）— P2

**结论修正（第三条实测）**：DSH 的 `min(W×0.8, W−O−64K)` **不照抄**。代入 step-5-preview（1M 窗口）实算：

| | 计算 | 触发点 |
|---|---|---|
| 咱们现在 | `970,752 × 0.8` | **77.7 万** |
| DSH 公式 | `min(1,024,000 × 0.8, 1,024,000 − 32,768 − 65,536)` | **81.9 万**（比咱们还晚） |

那个 64K 绝对项只在**小窗口**下顶得住（256K 窗口：绝对项 16.4 万 < 比例项 20.9 万）。**它服务的是"防溢出"，不是"控时延"**——照抄解决不了我们的问题。

**改造**：

1. **保留预算（真正起作用的那条）**：压缩后保留量从 `W × 0.65`（**63 万**）改为 **token 尾巴**——默认 `(W−O) × 16%`（1M 窗口下 **≈15.9 万**），并支持绝对量 `retainTokens`（小窗口用绝对值）。**这是压缩后工作集的直接上界，差 4 倍。**
2. **触发线补一条「独立于窗口的成本上限」**，与 `W×0.8` 取 min：
   - 纯 `W×0.8` 在大窗口下失控（77.7 万），DSH 公式同样失控（81.9 万）。**要压住峰值，必须有一条不随窗口缩放的线。**
   - **带宽要按「一轮能长多少」定，否则会疯狂压缩**：实测增长 = 普通轮 **+6K** / 重轮 **+20K**；例如 `T_high=160K → T_low=80K`（带宽 80K）→ 撑 **4~13 轮**才压一次。
   - **数值待实测标定，不照拍。**
3. **前置 pruner**（见 C 项）：先免费砍中段，砍完够轻就跳过摘要——控制增长速度的第一道。
4. 裁剪粒度从"完整轮"细化到**工具调用对**：一轮 33 次工具调用时，"整轮留 / 整轮丢"两头都不行。粒度到"对"为止，**不劈开进行中的调用对**；system 永不动。
5. **移除"当前轮硬保护"**：现有 `trimMessages` 保留**整个当前轮**，遇到超长轮就永远压不动——正是 DSH 刻意避开的那类坑。改为**靠尾巴预算保护近期**，兜底保留紧急裁剪（`trimCurrentTurn`）。
6. **上述参数全部改为可配置 + 支持按模型覆盖**（现在全是硬编码：16KB、6KB/4KB、0.8、0.65）。

### E. 时机与摘要（Harness）— P2

**改造**：

1. 压缩从"每次 `prepareTurn` 都可能触发"改为**Run 边界触发一次**，避免打断 Run 内前缀缓存。
2. 摘要请求**拼成上一请求的真前缀**（system + 上次工具 + 被压缩区域），复用 provider KV 缓存。
3. **校验摘要必须比原文短**，否则作废（避免花冤枉钱）。
4. 摘要事务留可审计标记（start / summary），崩溃留下未配对标记即视为锁。

## 实施顺序

1. **P0 · 图片轴预算** —— 改动集中（Runtime 物化点）、收益立竿见影（7.47MB → ~1MB），先做。**这是独立项，不属于「单条闸」。**
2. **P1 · 单条闸可恢复（spill）** —— 消除"砍掉就没了"，并把预算参数变成可配置。**这一条才是研究里逐条过的「第一条」。**
3. **P2 · 投影 + 保留预算 + 成本上限 + 时机 + 摘要** —— Harness 层成套改造，一起改才自洽。注意两点：**DSH 的阈值公式不照抄**（见 D 项结论）；**参数要可配、数值要实测标定**（不照拍）。
4. 每步同步更新 `docs/architecture-current.md` 的事件契约与模块表，并补回归测试。

## 验收标准

- 同一份 301K 上下文（含 **9 张历史图**），**HTTP 请求体 ≤ 1.5MB**（现在是 **7.47MB**）；"到响应头"从 28.6s 回到正常区间。
- 图片物化有硬预算：内联张数 ≤ `maxInlineImages`、base64 总量 ≤ `maxInlineImageBytes`。
- 被降级的图**以文字占位出现且带只读路径**，模型能按路径读回。
- 降级**成批且单调**：不因新图到来逐张重算、不因有余量而恢复；连续多轮请求的降级集合不变（前缀稳定）。
- transcript / checkpoint 里的图片引用**不被改动**（降级只影响模型视图）。
- 单条工具结果超限后，全文**落盘且模型能按 workspace 相对路径读回**中间内容；`read` 结果不被二次落盘（无循环）。
- 落盘失败时**保留原结果**（fail-soft）——宁可上下文大，不丢数据。
- spill 文件作为**运行时产物**：不触发"项目改动"语义，有清理策略（随会话删除或启动清扫），不残留孤儿。
- `tool_output_truncated` 事件可观测到"是否已落盘 + 落盘路径"。
- 长会话**工作集有上界**：压缩后回落到保留预算内（1M 窗口下 ≈**15.9 万**），而不是停在 63 万。
- **触发线在大窗口下也有效**：不只看 `W×0.8`——独立成本上限应先于它命中，且带宽经实测标定（不会每轮都压）。
- 压缩**只在 Run 边界**发生；Run 内前缀稳定、缓存持续命中。
- 摘要调用**命中前缀缓存**（观测 cacheRead），且摘要长度**严格小于**原文。
- **计量单一来源**：压缩决策、界面占用、观测事件取同一个数（`contextManager.process()` 的 usage），不存在各算各的。
- 参数**可通过配置调整**（不再硬编码），并支持按模型覆盖。
- 会话"越聊越慢"消失：相同任务下模型时间不再随轮数线性增长。
- `npm run test:all` 全绿，且新增改动**带回归测试**（Runtime 改动为硬要求）。

## 非目标

- **不改 Agent Loop 的控制流骨架**（调模型 → 调工具 → 再循环 → 收尾不变）。
- 不新增面向模型的 `artifact_read` / `artifact_search` 工具（沿用现有 `read` / `grep`）。
- **不做逐工具的保留配置**（目标是部署级默认行为，一个开关管所有）。
- 不引入成本预算 / 计费策略（本期只解决体积与时延）。
- 不改动 canonical transcript 与 checkpoint 的"永不删除"语义（投影只影响模型视图）。
