# Agent 按需规划调整建议

日期：2026-10-19  
状态：**已实施（提示层）** —— 2026-10-19 按第 5 节范围完成四处提示与两处渲染文案修改，测试断言同步更新；真实模型行为验证（第 6.2 节场景）未进行。  
源码核对基线：`986a1d7`（建议稿）；实施基线为实施时的 main。

## 1. 背景

此前项目针对 Agent 长时间执行、重复探索和任务收尾不明确等问题，进行了执行收敛治理。用户现在希望在保留必要约束的同时，让 Agent 自主选择工作方式，避免每个任务都先列一份任务清单。

本次反馈的具体场景是：用户只输入“先熟悉，当前改造。”，Agent 回复“先建任务清单，再读关键文件剩余部分”，随后展示六项计划，内容包括阅读执行预算实现、熟悉 Harness 与 Host 接线、核对测试入口、运行验证和汇总。截图中的任务由用户主动停止。

用户的诉求是：“能不能让 agent 自由点。不要每个任务都出任务清单。”

本次调整要解决的是规划方式过于固定。对于熟悉代码、解释问题和查看状态等任务，Agent 应能直接调查并回答；对于复杂开发任务，仍可自行选择使用计划。

证据边界：截图证明该次任务先建立了清单，不能证明所有任务都会建清单，也不能据此认定计划机制是此前长 Run 的全部原因。本次没有重新分析该 Run 的完整事件或测量计划调用的耗时占比。

## 2. 当前原因

源码中有四处重复强调“先建清单、逐项立即更新”：

| 位置 | 当前规则 | 影响 |
| --- | --- | --- |
| `PAYASO.md` 的“任务计划”段 | 需要 ≥3 步或多次工具调用，先用 `updatePlan` 列计划再动手 | 多文件阅读也容易触发先建计划 |
| `src/harness/instructions.ts` 的 `planningSystemPrompt()` | 三步以上，开始前发布清单；每项完成时立即更新 | 将步数作为规划触发条件 |
| `src/tools/plan-tools.ts` 的工具描述 | 多步任务开始时先建计划，每完成一项立即更新 | 工具说明继续强化固定流程 |
| `src/harness/plan.ts` 的结果文本和上下文投影 | 完成一项后立即提交更新后的完整清单 | 建立计划后持续推动细粒度更新 |

这些是模型可见的提示要求，并非 Runtime 对“无计划执行”的机械拦截。现有机制允许没有计划的任务正常执行与结束。因此，优先统一调整提示规则即可，不需要新增复杂度判断器。

仅修改一处容易留下冲突。例如，系统提示允许按需规划，但项目约定仍要求多次工具调用先建计划，Agent 仍可能选择先列清单。

## 3. 调整目标

核心原则：**计划可选、按需使用、按阶段更新。**

1. **由 Agent 判断计划是否有价值。** 不再以“三步以上”或“多次工具调用”作为必须建计划的条件。
2. **普通任务自然执行。** 熟悉代码、解释问题、定位原因、查看状态和小范围修改，通常直接开展工作；需要交代方向时，简短说明即可。
3. **复杂任务允许规划。** 多个交付目标、明显依赖关系或需要阶段跟踪时，Agent 可以使用计划。这些是判断参考，不作为新的硬性触发器。
4. **尊重用户明确要求。** 用户要求先出计划或方案时，先提供相应内容；这不自动构成实施授权，也不要求额外创建一份重复的工具清单。
5. **按阶段更新。** 阶段完成、方向变化、出现阻塞或准备交付时维护计划，允许合并更新，不要求每次读文件、执行命令后更新。
6. **计划不得扩张任务。** 用户只要求熟悉或分析时，不因计划中列了测试、修改、提交或发布就自行执行。调查中可以提出建议，后续行动仍应符合用户授权范围。
7. **状态保持真实。** 使用计划时，完成、进行中和待办应反映实际进展；未完成就说明原因，不为清空待办执行额外事项，不把“计划全部完成”当作交付通过的证据。

## 4. 建议统一采用的规则文案

以下内容可作为四处提示修改时共同遵循的语义，各位置按职责简化，避免重复堆叠：

> 计划是可选的工作工具。根据当前任务，自行判断是否需要使用 `updatePlan`；不要仅因步骤较多或需要多次工具调用，就先建立清单。普通调查、解释和小范围修改通常直接开展。对于需要阶段跟踪或协调多个交付目标的工作，可以使用计划。用户明确要求先提供计划时，遵从其要求，并区分方案输出与实施授权。使用计划后，在阶段进展、范围变化、阻塞或交付时更新，可合并更新；保持状态真实，不为维护清单增加用户未要求的工作。

工具说明应着重描述它的用途和参数语义：提交完整计划、全量替换、状态取值、清空方式等。“多步任务先建计划”和“每完成一项立即更新”应移除。

计划结果文本和上下文投影只需提供当前进度，并提示在重要进展或变化后更新，不再反复催促“立即更新”或“开始下一项先更新”。

## 5. 修改范围与保留机制

| 文件 | 建议修改 |
| --- | --- |
| `PAYASO.md` | 将计划约定改为按需使用，移除步数、调用次数和逐项立即更新的要求 |
| `src/harness/instructions.ts` | 调整 `planningSystemPrompt()`，统一为自主判断、普通任务直接执行 |
| `src/tools/plan-tools.ts` | 放宽工具描述，保留完整清单、状态和参数说明 |
| `src/harness/plan.ts` | 调整 `renderPlanResult()` 与 `renderBoundedPlanView()` 中的维护提示 |
| `tests/plan-state.test.ts`、`tests/plan-view.test.ts`、`tests/plan-loop.test.ts` | 同步移除对旧“立即更新”文案的依赖（实际实施中发现 plan-loop 亦有一处），保留对状态、进度和投影正确性的验证 |

首轮保留现有计划工具、事件协议、状态校验、持久化、恢复和前端进度展示。已有计划在收尾时仍应如实反映实际状态，保留现有一次性收尾提醒及审计机制。

执行预算、重复调用治理、权限限制和交付核查继续承担各自职责。自主选择是否规划，不改变用户目标或执行授权。

本轮无需新增规划模式开关、任务分类服务、自动复杂度评分或 Agent Loop 分支，也不通过隐藏前端计划面板来代替行为调整。

## 6. 验收建议

### 6.1 确定性验证

- 四处模型可见规则语义一致，不再要求按步数或工具调用次数建计划。
- 未调用 `updatePlan` 时，可正常执行、答复和结束，不出现缺少计划的错误或补计划要求。
- 已使用计划时，完整替换、状态校验、事件投影和恢复机制保持有效。
- 多项进展可以合并为一次更新；收尾时未完成事项仍如实记录。
- 更新相关文案断言，不能只删除原有状态与恢复验证来让测试通过。

### 6.2 真实模型场景

| 场景 | 输入示例 | 验收关注点 |
| --- | --- | --- |
| 熟悉现状 | “先熟悉当前改造。” | 能直接阅读并总结，不机械先建清单，不自行升级为修改或跑套件 |
| 多文件调查 | “看看这几个模块怎么连接。” | 多次读取不自动等于必须建计划，最终回答有源码依据 |
| 小范围修复 | “修一下这个按钮文案。” | 自主选择简洁路径，完成必要检查后收尾 |
| 复杂功能开发 | “实现历史任务搜索，并完成相关验证。” | 可自主选择计划；选择后按阶段维护，最终交付可验收结果 |
| 明确要求方案 | “先给我修改计划，暂时不要改代码。” | 提供方案，遵守只分析的边界 |
| 中途纠正范围 | “先别继续实现，只告诉我当前情况。” | 按最新要求答复，不为完成原清单继续执行 |
| 阻塞与未完成 | 某个阶段因外部条件无法继续 | 如实说明阻塞和剩余事项，不为了更新清单制造完成状态 |

真实模型验证应记录实际 `updatePlan` 调用、工具行为和最终答复，区分“提示已修改”和“行为已验证”。对存在波动的场景做必要复测，不能用一次通过或固定回复的模拟 Provider 证明模型行为已经稳定。

验收允许不同任务采用不同工作方式；不追求“任何任务都不能使用计划”。判断重点是计划是否有助于当前任务，以及是否造成重复维护或范围扩张。

## 7. 实施与交付要求

实施时先确认当前分支和用户未提交改动，按上述范围修改。先完成相关定向验证，再根据实际风险决定是否扩大验证范围；检查提示规则与状态机制的结果，应和真实模型行为结果分别报告。

交付说明应列出实际修改、验证结果和未验证内容。未经用户后续授权，不推送、不发包。
