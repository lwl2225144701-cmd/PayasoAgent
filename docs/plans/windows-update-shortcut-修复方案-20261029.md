# Windows 更新后快捷方式与自动重启修复方案（2026-10-29）

> 状态：已按本方案实现 v0.4.23 候选代码，正在验证，尚未正式发布。v0.4.21 → v0.4.22 的 Windows 实机验收未通过：新版本安装成功，但更新后的自动启动被快捷方式错误提示打断，需要手动双击恢复后的图标才能打开。
>
> 前轮修复及发布证据见 [故障排查记录](windows-update-shortcut-故障排查-20261029.md)。本方案不把“图标后来补回”作为更新完成。

## 1. 现场结论

用户已确认更新为 v0.4.21 → v0.4.22，手动启动后显示 0.4.22。具体过程为：下载 → 安装并重启 → 出现目标路径改变、询问删除快捷方式的提示 → 删除后图标稍后恢复 → 自动重启未完成 → 手动双击图标可以启动。

可以确认新版本已写入且可运行，失败集中在快捷方式处理与更新后的自动启动交接。图标恢复说明安装器或程序侧的某个补建分支起作用，尚不能确认是哪一个进程执行了补建；不能仅据此认定新程序此前已成功启动。

## 2. 为什么路径可能变化

当前锁定的 electron-builder 26.15.3 NSIS 模板有以下顺序：

1. 新安装器读取已安装版本的卸载程序，将其复制到临时位置后执行；因此升级到新版时，卸载旧文件的代码仍来自旧版。
2. 旧卸载程序的 `un.atomicRMDir` 将安装目录中的旧文件逐个 `Rename` 到 `$PLUGINSDIR\old-install`，然后清理原目录。
3. 新安装器写入新文件，处理快捷方式，执行项目的 `customInstall`，最后尝试启动新程序。

依据位于当前依赖目录中的 `installSection.nsh`、`include/installUtil.nsh`、`uninstaller.nsh` 和 `common.nsh`，均在 `apps/desktop/node_modules/app-builder-lib/templates/nsis/` 下。

Windows 快捷方式可以按对象标识跟踪目标。微软说明，重命名或移动会保留对象标识，链接解析可寻找目标的新位置。因此保留的旧链接可能追随被移走的旧 EXE；新 EXE 即使写回相同的文本路径，也不能据此证明旧链接已指向新文件。见 [Microsoft：链接跟踪与对象标识](https://learn.microsoft.com/en-us/windows/win32/fileio/distributed-link-tracking-and-object-identifiers)。

**证据边界**：旧文件移动是源码确认；该机快捷方式是否实际指向 `old-install`、Windows 在哪个时刻解析并保存了链接，仍需读回实际目标和安装日志。当前不能排除公共目录中的另一份链接、安装范围或运行时启动目标错误。

另一个必须解释的矛盾：v0.4.22 的 `customInstall` 已将 `$launchLink` 设为 `$appExe`，但实机仍出现快捷方式提示。后续不能重复提交“改成 EXE 路径”作为已证明的根治；必须记录最终传入启动调用的真实路径、启动返回值和新进程就绪结果，确认弹窗来源。

## 3. 修复顺序

### 3.1 先补齐安装阶段的证据

安装器记录每个阶段的时间、安装范围、安装目录、旧卸载程序路径、旧/新 EXE 路径、桌面和开始菜单链接位置及原始目标、最终启动目标、启动调用结果。新程序记录 PID、实际 EXE、版本及窗口就绪时间。

读取链接用于诊断时先取原始目标，不调用会触发修复的 Resolve，避免取证操作改变现场。诊断不得仅在写入失败时记录；也不得只比较路径字符串就宣告整条更新流程成功。

这些证据用于区分“链接追随旧 EXE”“处理了错误的链接位置”“未使用预期的 EXE 启动路径”和“进程启动后提前退出”。

### 3.2 把旧链接处理提前到旧文件移动之前

- 在应用确认退出后、调用旧卸载程序前，按注册表安装范围和 Windows Known Folder API 找到本安装管理的桌面/开始菜单链接。
- 记录链接是否存在及其属性；备份后移除需重建的旧链接，使安装器不再跨文件移动阶段保留这些链接。
- 新文件落盘并校验成功后创建新链接。更新前已不存在的用户自删图标不应无条件恢复；旧链接处理失败需记录原因，不能静默继续声称修复成功。
- 安装取消或旧卸载失败且原 EXE 仍可运行时，按快照恢复原链接；原文件已替换时，按当前有效 EXE 重建，不能盲目恢复指向临时目录的旧链接。

**实现约束**：现有 `customInstall` 在旧卸载之后，太晚。需在受控的安装脚本中为“调用旧卸载前”增加明确插入点，并锁定上游模板版本、检测调用顺序。不能只新增新版 `customUnInstall` 就声称能修复 v0.4.22 → 下一版，因为该次运行的是 v0.4.22 已安装的旧卸载程序。也不建议直接替换上游文件删除/恢复算法，以免破坏被占用文件的回退行为。

### 3.3 创建面向固定安装路径的链接

使用 Windows Shell COM 接口统一创建、保存并读回本安装管理的链接，明确设置目标 EXE、工作目录、图标和 AppUserModelID。使用 `IShellLinkDataList` 设置禁用目标对象/路径跟踪的标志，保存后验证标志及目标。

微软提供 `SLDF_FORCE_NO_LINKTRACK` 和 `SLDF_DISABLE_LINK_PATH_TRACKING`；具体标志组合需通过真实文件移动试验确认，见 [Microsoft：SHELL_LINK_DATA_FLAGS](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/ne-shlobj_core-shell_link_data_flags)。这属于拟实施方案，尚未验证其在当前 NSIS/Electron 环境中的效果。

安装器和程序兜底必须使用同一套创建方式，避免程序侧后续调用普通 `writeShortcutLink()` 又生成未带相同标志的链接。只操作本应用管理的链接，不修改系统链接跟踪服务、组策略或其他应用快捷方式。公共链接按真实安装范围处理，不能在无权限时留下同名错误副本却记成功；用户改名和任务栏固定副本单独列验收范围，不盲目扫描覆盖。

### 3.4 自动启动与链接修复解耦，并确认新程序就绪

- 等待旧进程退出及安装器完成文件替换，使用校验后的 EXE 绝对路径和显式工作目录启动，启动入口不使用 `.lnk` 或依赖 Explorer 对链接的解析。
- 当前用户安装优先走同用户的进程创建；管理员安装需显式以原交互用户身份启动，不能直接继承管理员权限。原有提权与用户身份语义需要保留。
- 启动方必须得到错误码/PID，并等待新版本的就绪回执。回执包含版本、实际 EXE 和本次更新的唯一标识；只有进程被创建不能算重启成功，也不能误接收旧进程回执。
- 对启动失败、就绪超时和提前退出保留可诊断结果，给出重试/手动打开入口；不要以打开快捷方式作为失败回退。
- 安装器仅在新文件确认完成后启动一次；程序侧 3/10/30 秒修复可暂留兜底，不承担“先启动成功才能修图标”的主要职责。

## 4. 改动范围

| 位置 | 拟改动 |
|---|---|
| `apps/desktop/build/installer.nsh` 及受控安装段 | 增加旧卸载前链接快照/移除/恢复、安装阶段日志和实际启动交接。 |
| `apps/desktop/electron-builder.yml` | 接入受控安装脚本/辅助程序，保持安装标识及默认安装目录稳定。 |
| Windows 链接与启动辅助程序（拟建） | 通过原生 Shell/进程 API 管理链接标志、读回、启动身份和就绪回执；作为安装器与程序的共同实现。具体承载方式在验证最小原型后确定。 |
| `apps/desktop/src/windows-shortcut.ts`、`apps/desktop/src/main.ts` | 接入统一链接逻辑和新程序就绪回执；兜底不得覆盖禁跟踪标志。 |
| `apps/desktop/src/update/windows-installer.ts` | 如需外部交接监督，接入旧 PID、安装结果与启动结果；保持下载校验、NSIS 参数和提权回退。 |
| `tests/desktop-update.test.ts`、`.github/workflows/ci.yml` | 保留协议回归，新增 Windows 原生链接和真实升级验收；源码正则检查仅用于接线。 |

## 5. 验收与发布策略

1. **Windows 原生机制试验**：在临时目录创建真实 EXE/链接，将旧文件移动到 `old-install` 并写入新文件；比较普通链接和新策略的原始目标、跟踪标志及启动结果。验证中文空格路径和普通用户权限，取得修复前后的差异证据。
2. **真实旧版升级**：必须用已发布 v0.4.22 作为旧端更新到候选包，证明新安装器能应对旧卸载程序。确认全程无快捷方式删除提示、无需手动双击、新版本窗口自动出现且版本正确。
3. **链接稳定性**：更新后立即、30 秒后、程序退出后分别从桌面和开始菜单启动；校验已安装目录、原始目标和标志。检查用户自删图标、公共安装、提权取消、文件占用及安装失败恢复。
4. **连续升级**：再用修复后的版本更新到下一候选版本，确认新卸载程序及统一链接创建逻辑不会回退。
5. **发布门槛**：先生成候选产物，Windows 原生测试及真实 v0.4.22 升级验证通过后再正式发布。当前流程允许构建后直接发正式包，需要增加相应验收步骤。Mac 流程保持独立。

## 6. v0.4.23 候选实现

- 独立交接工具源码位于 `apps/desktop/windows/PayasoUpdate.cs`，由 Windows 自带的 .NET Framework 编译器生成。安装器在旧卸载之前调用它保存快照、分离链接；新文件落盘后重建并读回禁跟踪链接，失败/取消时尝试按快照恢复。
- `apps/desktop/scripts/package-windows.mjs` 保留上游卸载器生成、签名与文件替换流程，只在传给 makensis 的脚本中增加两个受控插入点。锁定 app-builder-lib 版本及模板 SHA-256，模板改变时拒绝构建；不修改 node_modules。
- 安装器调用独立工具直接创建新 EXE 进程并等待命名管道回执。回执核对本轮随机标识、真实管道客户端 PID、版本及实际 EXE；窗口内容挂载且后端可用后才发送。旧应用退出不会终止监督工具。
- 当前用户安装以当前用户直接创建进程；提权安装从同会话 Explorer 取得交互用户 token，再以该用户身份启动。找不到交互会话或权限不足时明确失败，不回退到管理员身份启动应用。
- 程序兜底复用相同原生工具，只处理已有链接；安装交接期间由安装器独占链接事务，避免新旧修复方式同时覆写。
- 新增 `tests/windows-update-native.mjs`，在 Windows CI 中编译真实工具，验证链接标志、卸载前分离、文件移动后重建、失败恢复、用户删除图标，以及真实进程/管道的就绪、错误版本和提前退出。CI 测试构建仅跳过 headless runner 的管理员降权路径；该路径仍需真实交互会话验收。
- 候选 CI 生成 Windows 安装器与更新文件到 Actions artifacts，不推送版本标签、不上传正式 Release。真实 v0.4.22 → 候选包完整升级、管理员交互会话及 Explorer 弹窗行为仍待验收。
