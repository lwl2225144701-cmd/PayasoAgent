# 流式回复实时渲染 Markdown（分块增量解析）

> 状态：已实施（commit `45419df`）。本文是该改造的完整记录：问题、原理、实现、实测、
> 边界与验收证据。
>
> 前置：`docs/streaming-render-optimization.md`（第一轮，commit `dba4101`）。**本文反转了
> 那份文档 §3① 的一个取舍**，反转理由见 §2。

---

## 1. 问题

流式回复期间，前端**不渲染 Markdown**：`**加粗**`、`- 列表`、` ```代码块``` ` 全部以原始
符号显示，直到整轮结束才一次性变成排版后的样子。

这不是 bug，是第一轮的**刻意取舍**：`dba4101` 把 `CollapsibleText` 的流式分支降级成
`pre-wrap` 纯文本，用来消灭「每帧对整条累计消息做 react-markdown 全量 parse」的开销。

取舍有效，但代价用户看得见。用户明确要求恢复实时渲染。

## 2. 为什么不能直接改回 `ReactMarkdown`

因为那会原样带回第一轮已经消除的性能问题。`react-markdown@10` 无内部缓存，每次渲染都
对输入整体 `runSync(parse)`：

- 流式期间文本**每帧都在增长**；
- 每帧全量解析 ⇒ 成本随累计长度线性上涨 ⇒ 总成本 O(文本 × 帧数)；
- 实测（10KB 大表格）单帧 12.4ms，第一轮文档记录的 16KB 重语料是 20.8ms，均已超一帧预算。

所以必须**换一条路**：不是「解析 or 不解析」，而是把每帧要解析的量从「全文」降到「尾部」。

## 3. 原理：块级结构一旦定型就不会再变

核心观察：

> Markdown 的块级结构一旦被**空行**终止，后续追加的内容只会形成**新块**，不会回头改写
> 已终止的块。

于是把累计文本切成三部分：

| 字段 | 含义 | 每帧成本 |
|---|---|---|
| `blocks` | 已定型块（空行终止、且不在 fence 内） | **0** —— 文本不变则 memo 跳过整个解析 |
| `tail` | 仍在写入的当前块 | O(尾部)，与累计长度无关 |
| `openFence` | 未闭合 fenced code 的**代码正文**（不含 ` ``` ` 开始行）；`null` = 不在 fence 内 | 0 —— 按纯代码渲染，不做 Markdown 解析 |

`openFence` 的两个语义细节（都有测试锁定）：

- **必须是正文，不含开始行**。最初实现返回的是从开始行起的整段源码，渲染出来就是字面的
  ` ```ts ` —— 用户会在代码块里看到它。已修正。
- **用 `null` 而非空串表示「没有未闭合 fence」**：fence 刚开启、正文还没到字符时正文也是
  空串，两者必须区分。

总成本从 O(文本 × 帧数) 变为 **O(文本) + 每帧 O(尾部)**。

### 唯一的复杂点：fence 会跨越空行

代码块**内部允许出现空行**，所以「凡空行即块边界」是错的——那会把代码块从中间切开。
扫描必须跟踪 fence 状态，且要处理 CommonMark 的细节：

- 支持反引号与波浪号两种 fence；
- 开始行允许 ≤3 个前导空格（4 个空格是缩进代码，不是 fence）；
- 闭合 fence 不得短于开始行（` ``` ` 闭合不了 ` ```` `）；
- 反引号 fence 的 info string 里不允许再出现反引号。

## 4. 实现

| 文件 | 职责 |
|---|---|
| `web/src/components/streaming-markdown.ts` | 纯函数：`splitStreamingMarkdown()` 单趟字符扫描（无正则、无解析）+ `normalizeFences()`（自 `CollapsibleText` 迁入） |
| `web/src/components/MarkdownText.tsx` | 抽出裸渲染器 `MarkdownContent`；新增 `StreamingMarkdown` 与 `MarkdownBlock` |
| `web/src/components/CollapsibleText.tsx` | 流式分支由纯文本改为 `<StreamingMarkdown>` |
| `web/src/components/markdown-body.module.css` | 新增 `.plainTail`（超长尾部降级样式） |

`normalizeFences` 之所以要迁走：`StreamingMarkdown` 需要它做**逐块**修复，而它原本住在
`CollapsibleText` 里，留在原处会让 `CollapsibleText → MarkdownText → CollapsibleText`
形成循环依赖。

### 两个必须处理的正确性陷阱

**① 未闭合的 fence 绝不能交给 Markdown 解析器。**

`normalizeFences` 会给奇数个 fence 补一个闭合标记。若把「流到一半的 mermaid」交给它，
就会补出闭合标记、把半截图表当成完整图表交给 `MermaidBlock` —— 必然语法报错，用户会看到
错误提示闪烁后再消失。所以 `openFence` 单独成一个字段，按纯源码渲染成代码块。

**② 每个块不能各套一层 `.markdownBody`。**

`markdown-body.module.css` 里有：

```css
.markdownBody > :first-child { margin-top: 0; }
.markdownBody > :last-child  { margin-bottom: 0; }
```

若每块各套一层容器，这两条会对**每一块**生效，段间距会被整片吃光。因此所有块共用**同一个**
`.markdownBody`，只把裸渲染器 `MarkdownContent` 抽出来复用。

这个做法还有个额外收益：流式与终态的 DOM 结构完全一致，定型瞬间不会因结构变化而重排。

## 5. 实测

真实语料（`.data/payaso.db` 中最长的 `final_answer`，8404 字符）+ 项目自身解析栈
（react-markdown@10 + remark-gfm@4），按实测 delta 粒度 18 字符/帧逐帧推进：

A = 每帧全量解析（第一轮之前的老做法）；C = 本次分块增量。

| 场景 | 帧数 | A 每帧 | C 每帧 | 耗时改善 | @5/s | @62/s |
|---|---|---|---|---|---|---|
| 真实语料 8404 字符 | 467 | 2.47 ms | **0.13 ms** | **19.5x** | 0.1% | 0.8% |
| 稠密 Markdown 4279 字符（有空行） | 237 | 4.36 ms | 0.19 ms | 23.4x | 0.1% | 1.2% |
| 超长代码块 15306 字符（未闭合 → `openFence`） | 850 | 0.77 ms | 0.01 ms | 109.1x | 0.0% | 0.1% |
| 单段正文 12500 字符（**无空行**） | 694 | 0.91 ms | 0.91 ms | 1.0x ❌ | 0.5% | 5.6% |
| 大表格 10369 字符（**无空行**） | 576 | 12.49 ms | 12.38 ms | **1.0x** ❌ | 6.2% | **76.8%** ⚠️ |

百分数 = 单帧解析耗时应占单核的比例。`@5/s` 是实测的真实 commit 速率（模型输出速度决定），
`@62/s` 是 rAF 合帧的理论上限。

真实语料那行的每帧解析字符量：**1,967,002 → 63,087（降 96.8%）**。

## 6. 边界与降级（重要）

**不含空行的超长块无法分块。** GFM 表格是最现实的例子：表格内部没有空行，定型前整体都是
尾部，只能每帧整段重解析。上表最后两行显示这一点：10KB 表格 12.38ms/帧、改善仅 1.0x
（等于没优化），在 62 commit/s 上限下会吃掉 76.8% 单核。这与第一轮文档记录的
「16KB 重语料 20.8ms」是同一类场景。

因此 `StreamingMarkdown` 设了硬上界：

```ts
const TAIL_PARSE_LIMIT = 6000;
```

超过该长度的尾部退化为纯文本（`.plainTail`），等它被空行定型后再按 Markdown 渲染。

- 作用：把**无界风险变回有界**——单帧解析成本不再可能随文本无限增长。
- 代价：病态的巨型单块在流式期间短暂以源码显示。
- 触发概率：正常回复的单块远小于该阈值；代码块另有 `openFence` 通道、根本不参与解析。
  真正会命中的基本只有「巨表格」这一类。

## 7. 测试契约

`tests/streaming-markdown.test.ts`（17 项，已注册进 `run-all.ts`）：

- fence 内部空行**不**切块（核心）；
- 未闭合 fence → 前缀冻结成块、fence 源码单独返回、**不泄漏进 Markdown**；
- 短 fence 不能闭合长 fence；波浪号 fence；≤3 前导空格是 fence、4 个空格是缩进代码；
- 连续空行不产生空块；块尾部空白被裁掉；
- **不变量：逐字符追加时，每步至多最后一个块变化** —— 这是「块级 memo 跳过解析」成立的
  前提，一旦破坏，性能保证就不成立。

## 8. 验收证据（SSR 逐帧探针）

用 Vite SSR 管线加载**真实组件**（非复刻逻辑），把一条含标题/加粗/列表/代码块/表格的回复
逐帧推进，检查实际产出的 HTML：

| 进度 | 长度 | `<h2>` | `<strong>` | `<ul>` | `<pre>` | `<table>` |
|---|---|---|---|---|---|---|
| 18% | 28 | ✓ | ✓ | · | · | · |
| 35% | 55 | ✓ | ✓ | · | · | · |
| 50% | 78 | ✓ | ✓ | ✓ | ✓ | · |
| 72% | 112 | ✓ | ✓ | ✓ | ✓ | · |
| 90% | 140 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 100% | 156 | ✓ | ✓ | ✓ | ✓ | ✓ |

即：**18% 时就已渲染出标题与加粗，不需要等终态**。

> ⚠️ 上表**不能**读作「任意时刻都不会出现原始 Markdown 记号」。探针点恰好落在完整结构上，
> 而流式必然存在「结构尚未闭合」的中间帧 —— 见下。

### 8.1 流式渲染的可验收契约

初版验收标准里有一条「任意时刻可见文本不含 `**` / `## `」，**该标准不可实现**：解析器无法
预知后续字符，未闭合的 `**` 在 Markdown 语义上本来就该当普通文本。实测逐帧输出：

| 累计输入 | 实际渲染 |
|---|---|
| `这是 *` | `这是 *`（原始星号） |
| `这是 **实时` | `这是 **实时`（原始 `**`） |
| `这是 **实时加粗*` | `这是 *<em>实时加粗</em>`（**被解析成 `<em>`**） |
| `这是 **实时加粗**` | `这是 <strong>实时加粗</strong>` |

注意第三行：未闭合输入不只可能显示原始记号，还会先渲染成**不同语义**（`<em>`）再自我修正。
这是流式 Markdown 的固有性质，与分块方案无关。

因此契约修正为**可实现、可回归**的形式：

> 1. Markdown 结构**闭合并收到后**，原始 `**`、标题标记等不再残留；
> 2. 未闭合的代码 fence / Mermaid fence **不显示 fence 标记**，也不触发错误渲染。

第 2 条已由 `tests/streaming-markdown.test.ts` 锁定（`openFence` 只返回正文、且绝不进入
Markdown 解析器）；第 1 条由 §10「对照组一致」与终态整段解析保证。

### 8.2 Mermaid 安全性

- fence 未闭合时：输出含 `<pre>`（源码正文），**不含**任何报错文案 —— 证明半截图表没有进入解析器；
- fence 闭合后：交给 `MermaidBlock`（SSR 下显示其视口占位 `_deferred_`，因为 SSR 不执行
  effects；真实浏览器中渲染为矢量图）。

### 8.3 事故记录：`normalizeFences` 曾会吞掉正文（已修）

**症状**：一条回复里 `### 配套收尾` 及其后十余行全部渲染成代码块，且某行后半句凭空消失。

**根因**（三段规则串起来才显形，单看每条都"合理"）：

1. 模型在行内写 `` ``` ``（想表示反引号本身）。规则 1「行中出现的 ``` 推到独立行」用
   `([^\n`])(```+)` 匹配到了这个**行内** run 并把它提升成行首；
2. 规则 2「fence 行只保留语言标签」随即把该行剩余内容当「杂文」**删除** —— 这是实际的内容丢失；
3. 提升出的 fence 成了孤立的开始标记，规则 3 又把闭合 fence 补到**文档末尾**，
   于是中间十余行全部落进代码块。

**修正**：给规则 1 加两道闸 —— ① 只在 3+ 反引号 run **总数为偶数**（即不存在孤立 run）时
才提升；② 只处理「本行其后不再出现反引号」的形态（`` ``` `` 后面还有反引号 ⇒ 是行内写法）。
原则是**宁可少修，不可多修**：漏修只是排版不完美，误修会丢内容。

**影响面**（对库内 86 条 `final_answer` 实测）：修复只改变 **2 条**的渲染结果，且两条都是
**找回**了原本被吞掉的标题；没有任何回复因此丢失代码块。库中存的是原文，损坏只发生在渲染
时，所以这 2 条历史回复**无需数据迁移，刷新即恢复正常**。

**回归测试**：`normalizeFences` 此前零测试（这是它能长期潜伏的原因），现已补 6 项，
其中 2 项专门锁定该事故形态，另有 3 项防止原有修复能力退化。

## 10. 已知行为差异（已实测）

少数 Markdown 结构在流式期间与终态的渲染**不一致**，原因是它们被空行切开了；定型后自动修正。
以下两条已用 SSR 实测确认（对照组「普通多段 + 紧凑列表」则完全一致）：

- **松散列表**：`- 甲` 空行 `- 乙` 空行 `- 丙` 在流式期间渲染成 **3 个独立 `<ul>`**
  （`<li>甲</li>`，紧凑），定型后并回 **1 个 loose list**（`<li><p>甲</p></li>`）——
  列表项间距在定型瞬间会有一次可见变化；
- **引用式链接**：`[ref]: url` 定义与它的引用若被空行分到不同块，流式期间链接**解析不出**，
  显示为字面量 `[文档][ref]`，定型后才变成真正的 `<a>`。

这两类结构在模型输出中都不常见（列表通常是紧凑的、引用式链接少见），且只影响流式期间。

## 11. 仍未验证

> 已由真实浏览器验收通过的部分见 §8.4（A1/C1/C3/C4/B5）。下面这些**不在其中**。

- **没有可用的 Performance 录制。** §5 是 Node 侧 `renderToStaticMarkup` 的**解析**成本，
  不含 React reconcile / DOM layout / paint。分块导致每块多一个 memo 组件的实际开销，
  以及 >50ms 长任务数，都还没有可信数据 —— 用户实测时 DevTools 停录卡在 trace processing，
  **需要换一种取数方式**（页面内 `PerformanceObserver`）。
- A2/A4 只有观感结论：没有帧级位移数据、没有滚动位置采样，因此**不能宣称「零跳动」**。
- `TAIL_PARSE_LIMIT = 6000` 是按解析密度反推的阈值，没有在真实「巨型表格」回复上验证过
  降级观感。

## 12. 一句话总结

块级结构「一旦被空行终止就不再变」是这次改造的全部依据：已定型块 memo 掉解析，每帧只解析
正在写入的尾部，于是既能实时渲染 Markdown，又不退回 O(文本 × 帧数)。代价是**不含空行的
超长块分不掉**，用 `TAIL_PARSE_LIMIT` 兜成有界降级。
