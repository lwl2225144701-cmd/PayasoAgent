## 结论

这次改动主要涉及上下文占用环的显示口径和文案，实际工具执行很短。总耗时 **13 分 46 秒**，其中约 **13 分 23 秒**处于模型调用，工具调用累计约 **22 秒**。首次编辑发生在启动 **10 分 8 秒**后；此前已经过了 **23 次模型调用、43 次工具调用**，多轮在补充搜索与重复规划之间循环。因此，直接问题是模型迟迟未从调查转入修改，而 Harness 没有在任务进展停滞时帮助它收敛；并非文件读写或前端构建缓慢。

值得验证的机制线索是：前 23 次模型调用共生成约 **129,987 字符 reasoning**，但同期留在 assistant 正文中的内容只有 **439 字符**。Payaso 将 reasoning 写入 trace，却在构建下一轮 transcript 时移除；Scratchpad 的模型视图也只保留工具名和参数，不保留工具结果或模型已作出的判断。这可能促使模型反复推导，但单次轨迹无法证明两者有因果关系：模型已经能看到原始工具证据，不同兼容端点对历史 reasoning 的支持也不同。不能因为 pi 内存里保留完整 `AssistantMessage`，就断言它在同一模型上会更快；更不意味着应把原始推理全文回灌模型。

跨轮上下文与思考配置进一步放大每轮成本：当前 Run 从上一轮 checkpoint 继承了完整工具交互；首个模型调用的真实输入为 **43,859 token**。运行时选中的 `step-5-preview` 配置为 `high` 思考档。两者都是可观察到的放大因素；没有做相同任务的对照运行，不能单独量化各自贡献。

## 与现有运行控制的关系

Payaso 已有与 pi 同一类的基础控制，不能把这次问题归因于“没有重试上限或无法中断”：LLM 请求和工具执行都有有界重试/超时；Runtime 接受取消信号；工具执行前会阻止**同一工具、同一参数且已失败超过限额**的再次调用；非幂等操作有 checkpoint 与结果回放/不确定状态保护；Harness 还提供可选的 `shouldStopAfterTurn` 停止点。对应实现见 [`llm.ts`](../src/llm/llm.ts)、[`process-manager.ts`](../src/runtime/tool-invocation/process-manager.ts)、[`side-effect.ts`](../src/runtime/side-effect.ts) 和 [`agent.ts`](../src/runtime/agent.ts)。这些机制与 pi 的接口和覆盖范围不完全相同。

本 Run 在首次编辑前的 **43 次工具调用，其“工具名 + 参数”组合 43 次都不同**，且每次调用都增加了消息/工具结果。故“相同失败调用拦截”和“运行时状态没有变化”一类守卫不会命中；也没有发生崩溃重放或请求无限重试。空转发生在**任务目标层**：不同的搜索和读取持续产生状态变化，模型却长时间没有把已掌握的信息转化为改动。现有 `shouldStopAfterTurn` 是可接入策略的控制点，不能单凭控制点存在就认为已有任务进展判定。

## 机制分析

### 1. 调查结论没有沉淀为稳定的下一步决策

[`agent.ts`](../src/runtime/agent.ts) 将模型返回的 reasoning 留在 `llm_call` trace，却通过 [`context-harness.ts`](../src/harness/context-harness.ts) 的 `sanitizeAssistantMessage()` 从后续 transcript 中移除。这样做避免原始隐藏推理进入 checkpoint 和后续请求；本 Run 早期多数 assistant 正文为空，23 次模型调用的可见正文总共只有 **439 字符**。[`scratchpad-view.ts`](../src/harness/scratchpad-view.ts) 明确只投影最近工具名和输入，不投影结果或调查结论；`updatePlan` 记录的则是任务清单，不表示已有证据充分、该进入修改阶段。下轮能重读工具输出，但没有单独的精炼决策状态。作为对照，本机 `../pi/packages/agent/src/agent-loop.ts` 在内存上下文中保留完整 `AssistantMessage`；具体 provider 是否重放其 reasoning 取决于模型协议和适配器。这个差异是待测假设，不是本次异常的已证根因，也不能据此推断其他 Agent 普遍实现了语义级进展检测。

### 2. 旧 Run 的完整工具历史进入新 Run

[`run-lifecycle-service.ts`](../src/host/run-lifecycle-service.ts) 的 `conversationHistory()` 从最近 checkpoint 复用完整 transcript，包括旧工具调用与结果（约第 653–680 行）。这保证跨轮连续性，但把“熟悉项目”时的大量读文件结果带入了后续的小型 UI 修改任务。每发起一次新模型请求，仍可见的历史都随请求重新提交。

[`context-harness.ts`](../src/harness/context-harness.ts) 的自动摘要仅在预计输入超过模型输入预算的 **80%** 时触发（约第 479–484 行）。本 Run 最后一轮的估算输入约 **119,220 token**，远低于该模型约 **970,752 token** 的输入预算，因此从成本角度已经很长的上下文没有触发压缩。该阈值解决的是“放得下吗”，没有控制“每轮重复提交是否划算”。

### 3. 探索后缺少进度约束

[`agent.ts`](../src/runtime/agent.ts) 的主循环没有固定迭代上限（约第 195–199 行），同时提供可选的 `shouldStopAfterTurn` 控制点（约第 491–499 行）。此设计允许复杂任务持续推进；本 Run 没有接入针对“长时间未首次编辑”的任务进展策略，因此模型在已定位改动点后仍连续进行只读调用和重复规划。不能仅凭调用数量判定所有长任务都应终止；需要区分真实调查与无新增证据的空转。

### 4. `high` 思考档放大了空转成本

排查时，所选模型 `step-5-preview` 的设置是 `thinkingLevel: high`。多次规划回合的输出与等待时间明显较长，其中单次模型调用最长约 **82.6 秒**。这与总耗时吻合，但仍需 A/B 测试才能判断降低思考档对质量和耗时的净影响。用户选择的思考档不应被运行时静默覆盖。

## 解决策略

优先做一个有界的运行时进展提醒，并用同一模型、同一任务对照验证。单独压缩旧历史不能解释或消除首次编辑前的 **23 次模型调用**；仅拦截相同 `(toolName, args)` 也无法处理本案例，因为首次编辑前的 43 次调用全部具有不同参数。不能把“执行了工具”直接视为任务取得进展。

### 当前建议：一次性进展提醒 + 小样本对照

在工具回合边界，根据已有的工具副作用分类和 Run 时间统计“连续只读调查”。先以 **连续 8 个只读回合且已运行 2 分钟**作为实验触发条件；`updatePlan` 等中性工具不算文件修改，`shell` 等无法可靠分类的调用不据此触发提醒。条件满足时，Harness 在下一次模型视图里**只注入一次**简短提醒：核对用户目标与已有证据；足够则进入执行或答复，不足则指出阻碍下一步的具体缺口，再做针对性调查。提醒触发状态随 checkpoint 保存，并留下事件以便审计和恢复。

提醒只要求模型重新判断当前阶段；它不替模型决定“已经查够”，不阻断工具、不强制编辑，也不限制完成任务所需的修改范围。可在 [`instructions.ts`](../src/harness/instructions.ts) 的 Workflow 提示中补充一句“已明确下一步时及时执行”，但这只是辅助。用同一模型和思考档，对小型代码改动、复杂改动和只读调查做前后对照；看首次编辑时间、模型回合数、完成质量、误提醒和过早修改。效果不稳则撤回运行时提醒；只有反复复现仍显示任务停滞，才考虑下面的备选方案。**8 回合 / 2 分钟**与 **16–32K 历史阈值**都是待验证参数，不是已确认的正确阈值。

### 后续备选 A：保存简短决策状态，再做进展提醒

在模型视图中提供有界的任务状态：目标、已定位文件、已确认的证据、仍缺的具体证据，以及下一阶段动作。它应来自可见工具结果与明确的计划更新，随 checkpoint 保存；不复制原始 reasoning，也不把每条工具结果再塞进 Scratchpad。此状态用于帮助模型在工具回合后接着做，而不是每轮重新规划。先用本 Run 回放检查第 10 次调用后它是否能明确选择编辑；再评估是否需要模型生成或修订状态，以及由谁验证其准确性。

在 Runtime 的 turn 边界汇总现有事件，至少记录：本 Run 已用时间、模型调用数与累计 token、连续只读工具回合数、最近读过的路径或查询、计划 revision、首次写入/编辑时间及验证命令的结果。工具的 `effect` 已区分 `read`、`idempotent`、`non_idempotent`；对 `shell` 不能仅凭工具名判断是否只读，应按既有执行/工具结果语义分类，无法确认时不据此强制停机。保留事件和判定原因，便于回放审计。

对**明确要求改代码的任务**，若连续多轮只读且超过时间或 token 预算，先注入一次可信的进度提醒：概括已定位的文件与未完成目标，要求模型选择“开始修改 / 指出具体缺失证据并继续调查 / 明确阻塞”。阈值先以配置和观测数据确定，报告建议的初始实验点为 **8 个只读回合或 2 分钟未首次编辑**；这是待验证参数，不是代码正确性的硬规则。每个阶段限制提醒次数，避免提醒自身形成新循环。只读调查、总结任务和用户明确要求继续调研时不按“未写入”判停。

此方案可利用现有 `shouldStopAfterTurn` 控制点做**预算耗尽后的安全停止**，但该布尔钩子本身不会生成提醒；提醒需由 Harness/Runtime 在下一次模型视图中注入并持久化其触发状态。达到用户可见的总时长或用量上限后，应保存可恢复 checkpoint 并以 `stopped` 等明确状态结束，不能伪装成 `completed`，也不能跳过在途工具的副作用保护。

### 后续备选 B：在新 Run 边界控制历史输入成本

继续在 checkpoint 保存完整 canonical transcript，保证审计与中断恢复。新 Run 传给模型的历史视图采用独立投影：保留历次用户请求、最终答复、最近相关的工具证据；把较早且很长的工具结果转为可追溯摘要（文件路径、命令、退出状态、关键发现），必要时让模型重新读取原文件。对直接追问上一轮工具结果的任务，应优先保留那段证据，不能机械地只留最终答复。

在现有“接近上下文窗口才摘要”的容量阈值之外，增设**跨轮历史成本阈值**。例如以旧工具结果超过约 **16–32K token** 作为实验触发点，在新 Run 第一次请求前生成有界视图；阈值需通过真实任务回放决定。摘要或投影失败时保留当前可靠路径并记录原因，不静默丢失用户约束、附件引用或未完成工作。该策略解决的是 1M 窗口模型虽容得下旧历史、却在每轮反复为它付费的问题。

### 后续备选 C：约束验证方式与可选思考成本

修改项目指令和检查流程：定位受影响文件与验证入口后及时编辑；独立修改与检查尽量合并；测试失败时读取已有完整输出，避免为了换一个 `tail`/`grep` 切片重复执行。Shell 检查必须保留被检查命令本身的退出码。本 Run 的无效 `edit` 调用可作为工具参数修复回归样本，但不是 10 分钟首次编辑延迟的主因。

`thinkingLevel: high` 是用户的模型配置，不应自动改写。可提供每 Run 可见的思考档选择，并对同类任务做 `high` 与较低档的对照，记录质量与耗时；若收益明确，再考虑向用户推荐默认档次。

## 如果一次性提醒无效，再分阶段实施与验收

| 阶段 | 交付 | 验证重点 |
| --- | --- | --- |
| 1. 观测 | 首次实际修改时间、只读回合、模型/工具耗时与跨轮历史 token 的 Run 指标 | 使用本 Run 回放，计算值与持久化事件一致；不改变执行行为 |
| 2. 决策状态与软提醒 | 有界的已确认证据、缺口和下一阶段动作；可配置且有限次的进展提醒 | 小改动在查够证据后推进；大型只读调查不会被误催改文件；取消和恢复后不重复提醒 |
| 3. 历史投影 | 独立于 canonical checkpoint 的有界新 Run 模型视图 | 继续上一轮任务、引用旧结果、附件和中断恢复均保持正确；旧工具正文不再每轮整段重发 |
| 4. 用量刹车 | 可配置的时间/token 提醒与可恢复停止 | 超预算状态明确、可继续；无虚假完成或副作用重放 |

先在记录或影子判定模式下评估阈值，再逐项启用。用一组小型代码修改、跨轮追问和长篇只读调查做前后对照；比较首次编辑时间、总耗时、模型调用数、累计输入 token、任务完成质量以及误提醒/误停率。以本 Run 的 **608 秒首次编辑、45 次模型调用、333 万累计 token** 为问题基线，观察 P50/P90，避免只凭单次样本宣布修复。只有效率下降而正确性与连续性不退化时，才视为验收通过。
